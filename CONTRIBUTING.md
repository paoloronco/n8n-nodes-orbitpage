# Contributing

Thank you for improving the OrbitPage community nodes. This repository is
public, so contributions must contain only information and code that can be
published on GitHub and npm.

## Before you start

- Use a public issue for reproducible bugs, documentation problems, and feature
  proposals that contain no sensitive data.
- Report suspected vulnerabilities privately through [SECURITY.md](SECURITY.md).
- Keep a change focused. Discuss broad API or node-architecture changes before
  investing in a large implementation.
- Use respectful, technical communication and avoid including customer or
  tenant data in examples.

## Development environment

Use Node.js 22 or newer and install the locked dependencies:

```bash
npm ci
```

Run the local n8n development environment with:

```bash
npm run dev
```

The package declares runtime support for Node.js 20.19 or newer, while the
development and CI toolchain runs on Node.js 22.

## Repository conventions

- Keep runtime dependencies empty unless a concrete requirement has been
  reviewed. `n8n-workflow` remains a peer dependency.
- Preserve one output item and `pairedItem` linking for each input item.
- Preserve intentional `Continue On Fail` behavior.
- Keep authentication inside the n8n credential and transport helper.
- Never log credentials, signed upload URLs, authorization headers, or
  sensitive response bodies.
- Require HTTPS for non-localhost endpoints and do not weaken redirect or host
  restrictions.
- Prefer guided operations over special-case execution code.
- Keep private OrbitPage SaaS implementation details outside this public
  repository.

The programmatic action node is intentional because the integration combines a
large typed operation catalog with revision preflights, signed binary uploads,
item linking, and guarded custom paths. New special execution paths still need
a concrete reason and tests.

## Changing the API catalog

`nodes/OrbitPage/operations.ts` is the source of truth for guided operations.
When the public OpenAPI contract changes:

1. Verify method, path, `operationId`, scope, parameters, body requirements,
   revision source, and publish behavior.
2. Update the typed operation catalog.
3. Add editor properties only when the operation needs new input.
4. Add request-level tests in addition to catalog-count assertions.
5. Build and regenerate the operation matrix:

   ```bash
   npm run build
   npm run docs:generate
   ```

6. Review the generated diff.

`docs/OPERATIONS.md` is generated by
`scripts/generate-operation-docs.cjs`. Do not edit it manually.

## Documentation changes

The npm README should remain a concise first-use path. Put detailed procedures
in `docs/guides/` and add them to `docs/README.md`.

When behavior changes, update all affected surfaces:

- node field descriptions;
- generated operation metadata;
- focused guide;
- troubleshooting guidance;
- examples, when their behavior changes;
- `CHANGELOG.md` for user-visible release notes.

Use relative links for repository files so documentation works on both GitHub
and npm. Do not copy the generated operation table into hand-written guides.

## Tests and checks

Run the complete suite before opening a pull request:

```bash
npm run check
```

This runs lint, build, isolated package loading, generated-documentation
verification, and Vitest.

Add behavioral tests for the successful path and important failure modes,
especially for:

- revision and `If-Match` behavior;
- path parameters and custom-path validation;
- upload reserve, finalize, and cleanup;
- trigger baseline and state comparison;
- credentials and Base URL restrictions;
- item linking and `Continue On Fail`.

For documentation-only changes, also verify every relative Markdown link and
anchor. External links should point to primary OrbitPage, n8n, GitHub, or npm
sources.

## Pull-request checklist

- [ ] The change is limited to this public community-node repository.
- [ ] No token, signed URL, tenant data, customer data, or private SaaS code is
      included.
- [ ] `npm run check` passes.
- [ ] New behavior has regression tests.
- [ ] Generated files were regenerated rather than manually edited.
- [ ] Documentation and examples match the editor and runtime behavior.
- [ ] Compatibility or migration impact is explained.
- [ ] `CHANGELOG.md` is updated when users will observe the change.

## Versions and releases

Maintainers release the npm package through the checked-in GitHub Actions
workflow with provenance. Contributors should not create version tags or
publish the package from a pull request.

The npm package version and the n8n node version solve different problems. Use
semantic versioning for package releases; change the node version only when n8n
must preserve old stored workflow behavior. Parameter renames require an
explicit compatibility plan or fallback.

See [Development and release](docs/guides/development-and-release.md) for the
full repository layout and maintainer process.
